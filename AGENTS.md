# Agent notes for Hammock

Notes for coding agents, and people, working on Hammock. If `AGENTS.local.md` is beside this file, read it too: it's the maintainer's own (git-ignored), and where it differs from this file, it wins.

- **Worktrees go in `.claude/worktrees/<name>`** (git-ignored), on a branch of the same name: `just worktree onboarding` (or `git worktree add .claude/worktrees/onboarding -b onboarding`, or EnterWorktree; without `just`, copy `.signing-identity` (and `AGENTS.local.md`, if there is one) into it, or its β is signed ad hoc and loses privacy grants on every rebuild). Not in sibling folders next to the repo. A new worktree needs nothing built first: the `just` recipes that build link libghostty-vt from a cache shared by every checkout (`~/Library/Caches/hammock/ghostty`, built once per pinned Ghostty commit; `scripts/ghostty-deps.sh`). Don't build Ghostty in a worktree; if you build without `just` (plain `go build`, `swift build`, `xcodebuild`), run `just deps` first. **Tear a worktree down with `just worktree-remove <name>`**, not `git worktree remove` or a generic cleanup: it also stops that worktree's β, its daemon and panes and deletes its state dir (below), and refuses while anything still runs from the worktree's build. `just beta-prune` clears β state left by worktrees removed without it.
- Start with [README.md](README.md) (building and running) and [docs/build-plan.md](docs/build-plan.md) (the phases). Open work, follow-ups and known gaps are GitHub issues (below), not docs.
- Build and test in the dev app, β. Don't rebuild, kill or relaunch the installed `Hammock.app` or its daemon unless asked: it's the one the person at this Mac is working in.
  - **Each checkout has its own β.** In the main checkout `just mac-dev` builds the shared `dist/Hammock β.app` (state in `~/Library/Application Support/Hammock Beta`). In a worktree it builds that worktree's own, named after its branch: `dist/Hammock β <branch>.app`, with its own state dir (`Hammock Beta <branch>`), daemon, remote port and config file, so worktrees don't fight over one β or its daemon, and need no scratch daemon. It shares β's bundle id (privacy grants, notifications, UserDefaults), has no menu bar item (`BETA_MENU=1` to work on it), and its daemon isn't a login item: the app starts it. `scripts/beta-identity.sh` decides; `BETA_NAME=x` or `BETA_SHARED=1` override.
  - **β has its own config file**, in its state dir (`~/Library/Application Support/Hammock Beta/config`, or the worktree's), a copy of `~/.config/hammock/config` the first time it runs, so testing never changes the person's own settings. Its panes get `HMK_CONFIG_DIR`, and `just beta-env` sets it, so `hmk` changes that one.
  - `just beta` builds and (re)starts this checkout's β, only this copy, by path. `just beta-info` shows its app, state dir, socket and what's running (including a shared β daemon started from another checkout's build). `eval "$(just beta-env)"` points `hmk` at its daemon (it unsets the pane's `HMK_SOCKET`, which beats `HMK_DIR`). `just beta-clean` deletes a worktree's β (processes, state, app) without removing the worktree.
- **Merging a worktree branch into `main`:** rebase it onto `main` and fast-forward, or squash it into one commit. Never a merge commit (`git merge --no-ff`, or merging `main` into the branch): `main` stays linear.
- **Commits:** work on a branch, in a worktree (above), unless you've been told otherwise. Each commit is whole: the code, its tests and its release note (below) together.
- **The Xcode project** (`apple/iOS/HammockIOS.xcodeproj`: the iOS app, its notification extension, and the Mac app for Xcode Cloud) is Xcode's JSON format (`project.xcproj`, Xcode 27.2+), edited by hand or in Xcode and committed as it is, schemes included. Its targets build synchronized folders (`apple/iOS/Hammock`, `HammockNotify`, `Shared`, `apple/Sources/HammockMac`): adding, moving or removing a file needs no change to the project. Build settings live in `apple/iOS/Config/*.xcconfig`, with comments saying why; the Info.plist and entitlements files are plain files (Xcode's plist editor drops their comments, so edit them as text).
- **History before this repo** (to 2026-11-09, commit 831) isn't public. `scripts/history-commits` (831) keeps build numbers and release tags counting on from it.

## Issues

Open work, follow-ups and bugs are GitHub issues on `homegrownsw/hammock` (use `gh`). Mention new ones in your report.

- **Opening issues.** Open one only when you're asked, or when your work turns up something out of its scope; in that case say so in your report. Don't comment on, close or label issues you didn't open without asking. Give each one a Type (`Bug`, `Feature` or `Task`), set directly, rather than the `bug` and `enhancement` labels: `gh issue create --type Feature --title … --body …`.

## Adding features

- **Every change to app code adds a release note** for each app it reaches ([release-notes/README.md](release-notes/README.md)): `just note <mac|ios|both> <new|fixed|internal> "What changed."`, in the same commit. NEW and FIXED are read by the people using Hammock, so write them for them; INTERNAL never leaves the repo. `just note-check` says whether a change needs one (the daemon, CLI, TUI and helpers ship in the Mac app); `NO_RELEASE_NOTE=1` only for changes nobody will notice. Releases (`just release-mac`, `release-ios`, `release-apple`) freeze the pending notes into Sparkle's update window and TestFlight's What to Test, and push to `main`: the maintainer's to run, or an agent's when asked.
- **Every action goes everywhere it fits:** the Mac menu bar (with a shortcut, checked against macOS's own: ⌥⌘D is the Dock's, ⌥⌘T the toolbar's), the command palette (`CommandPalette.swift`, passing the same shortcut so it shows there: both take it from `Keys` in `Shortcuts.swift`, never a literal: each menu command is an action in `Keybinds.actions` (HammockKit) with its default, or none, so people can change it in Settings ▸ Keyboard and the config file; tooltips that name a shortcut use `Keys.hint`), the relevant right-click menus, `hmk` (`cmd/hmk/main.go`, with its usage text) and the TUI's palette and menus (`internal/tui/overlay.go`), and an MCP tool if agents could use it. Think about the TUI and iOS versions too, not just the Mac.
- **A new daemon message** (`proto/hammock/v1/hammock.proto`, then `just proto proto-swift`) needs: its handler in `internal/daemon/conn.go`; a guest check in `share.go` (`checkGuest`: what a View or Drive member may do); routing in `peer.go` (`msgTarget`) so a guest's daemon sends it to the host; what an agent in a pane may do (`agentCheck` in `caller.go`: anything not listed there is refused to agents); the "only available on this Mac" list in `conn.go` if paired phones mustn't; and an audit entry when an agent changes something.
- **Settings people might edit by hand** live in `~/.config/hammock/config` (Ghostty syntax, `AppConfig.swift`): Settings writes the same keys, and each key is listed in the file's header comment (in `AppConfig.swift` and its copy in `hammockconfig.go`) and `AppConfig`'s doc comment. A setting read through views goes in `Prefs` (`Prefs.swift` in HammockKit; the Mac's own in `MacPrefs.swift`), which keeps it in the config file on the Mac and UserDefaults on the iPhone. UserDefaults and `@AppStorage` are only for state that isn't a setting: window frames, selection, collapsed Groups, drafts.
- **A new setting in Settings** gets a line in `SettingsIndex` (`SettingsNavigation.swift`: pane, section, label, other words people might search for) and `.settingAnchor(...)` with the same id on its row, so the sidebar's search finds it and jumps to it. A new pane gets a `SettingsTab` case, its place in `SettingsTab.sidebar`, an icon, a colour and a one-sentence blurb, and opens with `SettingsPaneHeader`.

## SwiftUI on the Mac

- **List rows:** `.listRowBackground` and `.listRowInsets` go outermost on a row; wrapped by later modifiers (gestures, `onGeometryChange`), the List stops seeing them. A gesture on a row must not take the List's click (selection): select explicitly or use `simultaneousGesture`. The List doesn't animate rows changing place, and doesn't draw a row outside its own bounds.
- **The toolbar band** is Hammock's own (`ToolbarBand`, AppKit's titlebar background is off): views under the toolbar must let clicks through, so the window still drags from there.

## Checking UI without a person

- `HMK_DEBUG_SNAPSHOT=/path/prefix` renders the window (light and dark) and dumps its views, split view and titlebar geometry; with `HMK_DEBUG_TAB=<name>` (and `HMK_DEBUG_ZOOM=<n>` to zoom its nth pane), `HMK_DEBUG_DELAY=<s>`, `HMK_DEBUG_PALETTE=1` (or `=<text>`, opened searched for it), `HMK_DEBUG_HOVER=1`, `HMK_DEBUG_SIDEBAR_SCROLL=<pt>` (start with the sidebar scrolled), `HMK_DEBUG_PEEK=1` (the hidden sidebar's peek panel open; pass `--args -sidebarHidden YES`), `HMK_DEBUG_NOTICES=1` (sample notification cards in the window), `HMK_DEBUG_SETTINGS=notifications|keyboard|appearance|agentview|workspace|devices|editor|window` (workspace: onboarding's drawing of the window, both layouts; window: the whole Settings window, sidebar included, on the pane given by `--args -settingsTab <name>`, searching `HMK_DEBUG_SETTINGS_QUERY`) (that Settings pane, to `<prefix>-settings-<light|dark>.png`; pick the notification style with `--args -notify-style in-app`: any config key given as a launch argument beats the file's, search the keyboard one with `HMK_DEBUG_SETTINGS_QUERY=<text>`), `HMK_DEBUG_PROMPT=plain|other|preview|tasks` (the agent view's question card with a made-up question, its own answer being typed, one with previews, or under a task list and PR and artifact chips, to `<prefix>-prompt-<light|dark>.png`), `HMK_DEBUG_CODEBLOCKS=1` (code blocks with long lines, wrapped and not, and a Markdown one as source and rendered, to `<prefix>-code-<light|dark>.png`), `HMK_DEBUG_COMPOSER=<text>` (the agent view's composer with `<text>` typed, start it with `!` for a shell command, under two `!` commands as the agent view shows them, to `<prefix>-composer-<light|dark>.png`), `HMK_DEBUG_COMPUTER_LOOK=symbols|emoji[:search]` (the icon and colour picker for the first linked computer, else this one, rendered to `<prefix>-look-<light|dark>.png`), `HMK_DEBUG_SCHEDULES=list|edit` (the Scheduled Tasks sheet, or the editor on the first schedule, opened at launch and also rendered on their own to `<prefix>-schedules-<light|dark>.png`: sheets aren't in the window's snapshot), and `HMK_CONFIG_DIR=<dir>` for a scratch config (make scratch dirs, and any scratch `HMK_DIR`, with `mktemp -d`, not a fixed path under /tmp). In a worktree, its own β (`just beta`) is usually all the isolation you need. For a throwaway state on top, start the scratch daemon first (the bundle's own `hmkd --dir <scratch>`: β shuts down one of another version and starts its own), then `open -n --env HMK_DIR=<scratch> …` the same app, and kill only that copy afterwards. Live layers (CALayerHost: browser and simulator content) and materials don't render faithfully in snapshots (the sidebar's list comes out blank): for the window as it's really drawn, add `HMK_DEBUG_CAPTURE=1` (β captures its own window with ScreenCaptureKit, to `<prefix>-window-<light|dark>.png`; the screen must be awake), and `HMK_DEBUG_CAPTURE_ZOOM=<n>` to then zoom and unzoom the tab's nth pane, capturing frames as it animates (`<prefix>-zoom-NN.png`). Give a scratch daemon's first launch after a rebuild a longer `HMK_DEBUG_DELAY` (10): β restarts it.
- **The iPhone without a Mac:** a Debug build launched with `SIMCTL_CHILD_HMK_DEBUG_SAMPLE=1 xcrun simctl launch <udid> com.homegrownsw.hammock` shows a made-up Mac (`apple/iOS/Hammock/DebugSample.swift`: Groups here and on a linked computer, agents working, waiting and done, scheduled tasks and their runs), nothing paired or sent. With it, `HMK_DEBUG_COCKPIT_TAB=groups|devices|settings` opens that tab, `HMK_DEBUG_PATH=schedules,schedule:<id>` pushes those screens onto Sessions (tab and pane ids too), and `HMK_DEBUG_BOTTOM=1` scrolls Sessions to Coming Up (a schedule's page to its runs); the sample Mac's theme is Tokyo Night unless `HMK_DEBUG_MAC_THEME=<name>|custom`, and `HMK_DEBUG_THEME_PICKER=1` (with the settings tab) opens Settings ▸ Theme. Screenshot with `xcrun simctl io <udid> screenshot`, after `xcrun simctl ui <udid> appearance light|dark`; boot a simulator of your own (`xcrun simctl create`) and delete it afterwards.
- **Agent view smoothness:** `scripts/agentreplay` plays a real Claude session into a pane, as if it were being written now (run it in a pane of a scratch daemon: hooks only count from a pane's own processes). With `HMK_DEBUG_JANK=<file>` a development build appends, every two seconds, the frames, hitches and rows rendered in the agent view (`JankProbe.swift`; `HMK_DEBUG_JANK_ROWS=1` also tracks rows jumping, at a cost to the timings). What someone sees is best measured from a screen recording (`xcrun simctl io … recordVideo`), frame to frame.
- Prod and β both run as process "Hammock": ask System Events for a window by the process's unix id, not its name. Restart β with `just beta` (or by its path or PID: `kill -TERM`, then `open -n <app>`), never `quit app id …` or `open -b`: every checkout's β has the same bundle id.
- Real clicks, drags and anything you have to see: ask the person to try it in β.
