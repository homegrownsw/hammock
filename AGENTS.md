# Agent notes for Hammock

Notes for coding agents, and people, working on Hammock. If `AGENTS.local.md` is beside this file, read it too: it's the maintainer's own (git-ignored), and where it differs from this file, it wins.

## This repository is public

Hammock is open source (MIT), and everything in it is public: code, comments, tests and their data, docs, commit messages, and the repo's issues and pull requests. None of it may carry private information, whatever the Mac you're working on has in front of you:

- **Nothing about the people working on it, or the Mac it's built on:** no names (other than as commit authors), email addresses, home paths (`/Users/<name>`), computer, device or host names, IP addresses, device IDs, Apple IDs, or employers and their clients.
- **No secrets:** no tokens, keys, passwords, certificates, `.release.env` values or 1Password item names.
- **Nothing from other projects on the machine:** don't name, quote, copy from or link to other repositories, private or not, or other projects in `~/Developer`, in code, docs, issues or commit messages. Describe the idea instead. Third-party open source Hammock uses is credited in THIRD_PARTY_NOTICES.md and the acknowledgements, and links to it are fine.
- **Placeholders instead:** `/Users/me`, `~/Developer/app`, `you@example.com`, `Studio` or `Sam's iPhone`, `100.64.0.2`, `acme/widgets#42`. Test data taken from a real session (an agent transcript, a log) is anonymised before it's committed: paths, names, repos, account ids and tokens.
- **Screenshots and recordings** in issues or pull requests show test data, not someone's real Groups, panes or notifications.

Private context for the maintainer (their machines, accounts, release credentials, private history) belongs in `AGENTS.local.md`, which isn't committed. Before committing, read your diff with this in mind.

## Working on Hammock

- **Worktrees go in `.claude/worktrees/<name>`** (git-ignored), on a branch of the same name: `just worktree onboarding` (or `git worktree add .claude/worktrees/onboarding -b onboarding`; without `just`, copy `.signing-identity` (and `AGENTS.local.md`, if there is one) into it, or its β is signed ad hoc and loses privacy grants on every rebuild). Not in sibling folders next to the repo. A new worktree needs nothing built first: the `just` recipes that build link libghostty-vt from a cache shared by every checkout (`~/Library/Caches/hammock/ghostty`, built once per pinned Ghostty commit; `scripts/ghostty-deps.sh`). Don't build Ghostty in a worktree; if you build without `just` (plain `go build`, `swift build`, `xcodebuild`), run `just deps` first. **Tear a worktree down with `just worktree-remove <name>`**, not `git worktree remove` or a generic cleanup: it also stops that worktree's β, its daemon and panes and deletes its state dir (below), and refuses while anything still runs from the worktree's build. `just beta-prune` clears β state left by worktrees removed without it. Make worktrees with `just worktree`, not EnterWorktree (whose branch names and setup differ). In a worktree session the harness refuses shell commands it can't tell stay inside the worktree: edit files with Edit or Write rather than heredocs or `python3 -` scripts, run git as one plain command from the worktree's root, and pass a long commit message with `git commit -F <file>`.
- **Shell, tests and builds:** the Bash tool's shell is zsh, where an unquoted glob that matches nothing aborts the whole command: quote globs (`--include='*.swift'`), or search with `git grep -n PATTERN -- '*.swift'` (tracked files only, so no worktrees or `dist/`). `just test` runs every Go package; `just test -run TestX ./internal/agents/` runs one, and `just test-quick` all but `internal/daemon`, which alone takes a few minutes: iterate on one package, and run the full suite once before committing, in the background. Daemon tests that only wait on real daemons (the membership ones) run side by side with `t.Parallel()`; one that changes a package variable (a hook, a timer) mustn't. `just vet` includes gofmt. The Mac app's Swift product is `HammockMac` (`cd apple && swift build --product HammockMac`). Releases, `just share` and the App Store recipes need the screen unlocked and the login keychain, which an agent's sandbox hides: run them outside the sandbox (`scripts/preflight` checks both before anything is built).
- Start with [README.md](README.md) (building and running) and [docs/build-plan.md](docs/build-plan.md) (the phases). Open work, follow-ups and known gaps are GitHub issues (below), not docs.
- Build and test in the dev app, β. Don't rebuild, kill or relaunch the installed `Hammock.app` or its daemon unless asked: it's the one the person at this Mac is working in.
  - **Each checkout has its own β.** In the main checkout `just mac-dev` builds the shared `dist/Hammock β.app` (state in `~/Library/Application Support/Hammock Beta`). In a worktree it builds that worktree's own, named after its branch: `dist/Hammock β <branch>.app`, with its own state dir (`Hammock Beta <branch>`), daemon, remote port and config file, so worktrees don't fight over one β or its daemon, and need no scratch daemon. It shares β's bundle id (privacy grants, notifications, UserDefaults), has no menu bar item (`BETA_MENU=1` to work on it), and its daemon isn't a login item: the app starts it. `scripts/beta-identity.sh` decides; `BETA_NAME=x` or `BETA_SHARED=1` override.
  - **β has its own config file**, in its state dir (`~/Library/Application Support/Hammock Beta/config`, or the worktree's), a copy of `~/.config/hammock/config` the first time it runs, so testing never changes the person's own settings. Its panes get `HMK_CONFIG_DIR`, and `just beta-env` sets it, so `hmk` changes that one.
  - `just beta` builds and (re)starts this checkout's β, only this copy, by path. `just beta-info` shows its app, state dir, socket and what's running (including a shared β daemon started from another checkout's build). `eval "$(just beta-env)"` points `hmk` at its daemon (it unsets the pane's `HMK_SOCKET`, which beats `HMK_DIR`) and puts β's `hmk` first on PATH. Test new `hmk` and MCP features with that one: the `hmk` on PATH, and the MCP tools an agent has, are the installed app's, even in β's panes. `just beta-clean` deletes a worktree's β (processes, state, app) without removing the worktree.
- **Merging a worktree branch into `main`:** rebase it onto `main` and fast-forward, or squash it into one commit. Never a merge commit (`git merge --no-ff`, or merging `main` into the branch): `main` stays linear. `just land <name>` does it all (rebase, fast-forward, push, `worktree-remove`, the branch deleted), from any checkout. Neither it nor anyone else can push `main` while a release runs: `scripts/release` keeps its `release:` commit on `main` unpushed until the build is done, and the pre-push hook (`.githooks/pre-push`, installed by `just deps`) refuses that commit, or `main`, from anywhere else meanwhile.
- **The iPhone app's App Store listing** (its text, App Review's notes, TestFlight's test information) is in `marketing/appstore/` ([its README](marketing/appstore/README.md)), pushed with `just appstore-push`: change it there, not on the App Store Connect website. Its What's New is the iPhone's NEW and FIXED release notes.
- **Commits:** work on a branch, in a worktree (above), unless you've been told otherwise. Each commit is whole: the code, its tests and its release note (below) together.
- **The Xcode project** (`apple/iOS/HammockIOS.xcodeproj`: the iOS app, its notification extension, and the Mac app, for archiving in Xcode) is Xcode's JSON format (`project.xcproj`, Xcode 27.2+), edited by hand or in Xcode and committed as it is, schemes included. Its targets build synchronized folders (`apple/iOS/Hammock`, `HammockNotify`, `Shared`, `apple/Sources/HammockMac`): adding, moving or removing a file needs no change to the project. Build settings live in `apple/iOS/Config/*.xcconfig`, with comments saying why; the Info.plist and entitlements files are plain files (Xcode's plist editor drops their comments, so edit them as text).
- **History before this repo** (to 2026-11-09, commit 831) isn't public. `scripts/history-commits` (831) keeps build numbers and release tags counting on from it.

## Issues

Open work, follow-ups and bugs are GitHub issues on `homegrownsw/hammock` (use `gh`). Mention new ones in your report.

- **Opening issues.** Open one only when you're asked, or when your work turns up something out of its scope; in that case say so in your report. Don't comment on, close or label issues you didn't open without asking. Give each one a Type (`Bug`, `Feature` or `Task`), set directly, rather than the `bug` and `enhancement` labels: `gh issue create --type Feature --title … --body …`.

## Adding features

- **Every change to app code adds a release note** for each app it reaches ([release-notes/README.md](release-notes/README.md)): `just note <mac|ios|both> <new|fixed|internal> "What changed."`, in the same commit. NEW and FIXED are read by the people using Hammock, so write them for them; INTERNAL never leaves the repo. An iPhone note is read on an iPhone, in TestFlight and the App Store: write it for the iPhone, in the iPhone's words (tap, touch and hold, swipe, the screen or the Groups tab, not right-click, the window or this Mac), even when the change is shared with the Mac. When the two apps would say it differently, add one note each (`just note mac …`, `just note ios …`) rather than one for both. One note per change people will notice, not per commit: a branch of many commits has one per feature. Hidden things (easter eggs) get none. `just note-check` says whether a change needs one (the daemon, CLI, TUI and helpers ship in the Mac app); `NO_RELEASE_NOTE=1` only for changes nobody will notice. Releases (`just release-mac`, `release-ios`, `release-apple`) freeze the pending notes into Sparkle's update window and TestFlight's What to Test, push to `main`, and deploy the website and docs from the release commit (`scripts/site-deploy`): the maintainer's to run, or an agent's when asked. An agent cuts one in two runs: the first opens its notes in an editor pane beside yours and waits until the person closes it (run it in the background, and tell them it's waiting on them), then prints the notes and stops with exit 3. Show the person those notes and ask whether to release them; only if they say so, run it again with `approved` (it says how).
- **Docs** ([site/](site/README.md), published at homegrownsw.com/hammock/docs): when a change alters what people do or see (a new feature, command, setting, permission or changed behaviour), update the hand-written page that covers it in `site/src/content/docs/`, in the same commit. The reference pages (config, shortcuts, `hmk`, MCP, agents) are generated from the source by `just docs-gen`: keep `hmk help`, tool descriptions and `keys.go` accurate instead. `just docs` must still build. Keep pages tight: say each thing once, on the page it belongs to, and link to it elsewhere; leave out reasons that don't change what the reader does, reassurance, and what the app tells people itself; leave every flag to the generated reference. Reread what you wrote for verbosity before handing it over. Review comments left in `just docs-dev` are listed by `just docs-comments`: fix each, then resolve it with a reply ([site/README.md](site/README.md)).
- **Every action goes everywhere it fits:** the Mac menu bar (with a shortcut, checked against macOS's own: ⌥⌘D is the Dock's, ⌥⌘T the toolbar's), the command palette (`CommandPalette.swift`, passing the same shortcut so it shows there: both take it from `Keys` in `Shortcuts.swift`, never a literal: each menu command is an action in `Keybinds.actions` (HammockKit) with its default, or none, so people can change it in Settings ▸ Keyboard and the config file; tooltips that name a shortcut use `Keys.hint`), the relevant right-click menus, `hmk` (`cmd/hmk/main.go`, with its usage text) and the TUI's palette and menus (`internal/tui/overlay.go`), and an MCP tool if agents could use it. Think about the TUI and iOS versions too, not just the Mac.
- **A new daemon message** (`proto/hammock/v1/hammock.proto`, then `just proto proto-swift`) needs: its handler in `internal/daemon/conn.go`; a guest check in `share.go` (`peerCheck`: what a View or Drive member's daemon may send); routing in `peer.go` (`msgTarget`) so a guest's daemon sends it to the host; what an agent in a pane may do (`agentCheck` in `caller.go`: anything not listed there is refused to agents); what your other computers may ask of this one (`ownerCheck` in `computers.go`) — `TestEveryClientMessageIsPlacedInEachGate` fails until the message is named in each of those four, or listed in the test as deliberately not there; the "only available on this Mac" list in `conn.go` if paired phones mustn't; and an audit entry when an agent changes something.
- **Settings people might edit by hand** live in `~/.config/hammock/config` (Ghostty syntax, `AppConfig.swift`): Settings writes the same keys, and each key is listed once, with its default and what it does, in `internal/hammockconfig/keys.go`, which makes the file's header comment (Go's, and the Mac's `ConfigHeader.generated.swift`: run `just config-header`) and the docs' config reference. A setting read through views goes in `Prefs` (`Prefs.swift` in HammockKit; the Mac's own in `MacPrefs.swift`), which keeps it in the config file on the Mac and UserDefaults on the iPhone. UserDefaults and `@AppStorage` are only for state that isn't a setting: window frames, selection, collapsed Groups, drafts.
- **A new setting in Settings** stands on its label, with no caption explaining it, and gets a line in `SettingsIndex` (`SettingsNavigation.swift`: pane, section, label, other words people might search for) and `.settingAnchor(...)` with the same id on its row, so the sidebar's search finds it and jumps to it. A new pane gets a `SettingsTab` case, its place in `SettingsTab.sidebar`, an icon, a colour and a one-sentence blurb, and opens with `SettingsPaneHeader`.

## SwiftUI on the Mac

- **List rows:** `.listRowBackground` and `.listRowInsets` go outermost on a row; wrapped by later modifiers (gestures, `onGeometryChange`), the List stops seeing them. A gesture on a row must not take the List's click (selection): select explicitly or use `simultaneousGesture`. The List doesn't animate rows changing place, and doesn't draw a row outside its own bounds.
- **Under the toolbar** is the detail's own backdrop (the sidebar's glass and tint, `emptyDetailBackground`), the same for either pane spacing: views under the toolbar must let clicks through, so the window still drags from there.

## Checking UI without a person

- **Debug hooks** (`HMK_DEBUG_*`): a development build renders, opens or records a state on its own, for the Mac window (`HMK_DEBUG_SNAPSHOT`, Settings panes, sheets, captures of the window as really drawn, zoom/split/float frames, movies) and the iPhone's demo with a made-up Mac (`SIMCTL_CHILD_HMK_DEBUG_SAMPLE=1`). Every variable is in [docs/debug-hooks.md](docs/debug-hooks.md): read it before checking UI, and add a new hook there. A recording the person sends, or captured frames: `scripts/frames <movie|dir> <out>` makes one contact sheet of the distinct frames to look at. A capture that fails because the screen is locked or asleep, or β lacks Screen Recording, says so: ask the person, don't retry or work blind.
- **Agent view checks:** after changing the agent view (`AgentViews.swift`, its rows, `AgentSession`), run `scripts/agentview-check/run`. It plays the scenarios in `scripts/agentview-check/scenarios.txt` (opening a long conversation, sending with tools straight after, the keyboard, reading while the agent works, Latest, earlier messages, going back and forth, a permission, a real session with `--replay`) in the iPhone's demo, on a simulator of its own, and reports what the view measured itself doing: blanks, rows snapping or bouncing, hitches, with a frame at each. It fails on a blank, snap or bounce. When you find a new glitch, add a scenario that shows it before fixing it. `--fast` builds optimised, for timings.
- **Agent view smoothness:** `scripts/agentreplay` plays a real Claude session into a pane, as if it were being written now (run it in a pane of a scratch daemon: hooks only count from a pane's own processes). With `HMK_DEBUG_JANK=<file>` a development build appends, every two seconds, the frames, hitches and rows rendered in the agent view (`JankProbe.swift`; `HMK_DEBUG_JANK_ROWS=1` also tracks rows jumping, at a cost to the timings). What someone sees is best measured from a screen recording (`xcrun simctl io … recordVideo`), frame to frame.
- Prod and β both run as process "Hammock": ask System Events for a window by the process's unix id, not its name. Restart β with `just beta` (or by its path or PID: `kill -TERM`, then `open -n <app>`), never `quit app id …` or `open -b`: every checkout's β has the same bundle id.
- Real clicks, drags and anything you have to see: ask the person to try it in β.
